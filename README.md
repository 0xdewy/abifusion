# abifusion

Build Solidity function ABIs from EVM bytecode by fusing three imperfect signals.

`abifusion` combines:

- **evmole** for selector discovery and argument structure
- **openchain.xyz / 4byte.directory** for exact text signatures
- **known-selector and known-interface tables** for offline and novel selectors

The result is a practical ABI builder that beats either static analysis or
signature lookup alone, while keeping every function annotated with its source.

## At A Glance

| Capability | Status |
| --- | --- |
| Function selector discovery | Yes |
| Function names | From signature DBs or fallback names |
| Exact input parameter types | 98.5% held-out accuracy |
| Output types | Not recovered |
| Events | Not in the runtime wrapper |
| Network-free mode | No, signature lookup accuracy depends on cache/network |
| Address-based CLI | Yes, via `--address` and `ETH_RPC_URL` |

## Why This Exists

Building ABIs from bytecode is messy because every single source lies in a
different way.

Signature databases know exact types like `bytes32` versus `uint256`, but public
selector databases contain spam, collisions, and missing selectors. Static
analysis has the opposite profile: evmole can recover argument structure from
bytecode without selector spam, but it cannot always distinguish equivalent EVM
shapes such as `address` and `uint160`.

`ABIFusion` uses each signal where it is strongest:

1. Run evmole to discover selectors and argument structure.
2. Look up selector candidates in openchain and 4byte.
3. Use evmole's structure to choose the best signature candidate.
4. Fall back to evmole, a known-selector table, or a generic selector name when
   no signature is available.

## Accuracy

The canonical evaluation is generated by:

```bash
python scripts/eval/run_evaluation.py
```

It uses a deterministic 80/20 split of 500 verified mainnet contracts, builds
the known-selector table from the training split only, and reports held-out
exact parameter-type accuracy.

| Metric | Result |
| --- | ---: |
| **Fusion held-out accuracy** | **98.5%** (1223/1241 functions) |
| evmole baseline (same split) | 90.3% |
| Training accuracy | 98.2% |
| Generalization gap | -0.4 pp |

Held-out category breakdown:

| Category | Accuracy |
| --- | ---: |
| Simple tokens | 99.3% |
| DeFi routers | 97.4% |
| DeFi AMM | 100.0% |
| Other | 100.0% |

See [eval_output/canonical_evaluation.md](eval_output/canonical_evaluation.md)
for the generated report.

## Installation

Python 3.8+. `uv` recommended.

```bash
git clone <repository-url>
cd abifusion

uv pip install -e .
```

Development tools:

```bash
uv pip install -e ".[dev]"
```

Research/data tooling without the full dev stack:

```bash
uv pip install -e ".[tooling]"
```

The recommended fusion path queries openchain and 4byte when selectors are not
already cached. Network failures degrade gracefully, but accuracy will be lower
when signature lookups are unavailable.

## Quick Start

### CLI

```bash
# Recommended: fusion path
abifusion fusion --bytecode "0x6080..."
abifusion fusion --bytecode-file contract.hex
ETH_RPC_URL="https://..." abifusion fusion --address 0x...
abifusion fusion --bytecode-file contract.hex --output-format abi
abifusion fusion --bytecode-file contract.hex --min-confidence medium
```

Example output shape:

```json
{
  "functions": [
    {
      "type": "function",
      "name": "transfer",
      "selector": "a9059cbb",
      "inputs": [
        {"type": "address", "name": ""},
        {"type": "uint256", "name": ""}
      ],
      "source": "signature+evmole",
      "confidence": "high",
      "candidates": [
        {"name": "transfer", "types": ["address", "uint256"], "source": "4byte"}
      ]
    }
  ],
  "metadata": {
    "function_count": 1,
    "evmole_selectors": 1,
    "extra_selectors": 0
  }
}
```

### Python

```python
from abifusion import ABIFusion

result = ABIFusion().reconstruct("0x6080...")

for fn in result["functions"]:
    types = ",".join(inp["type"] for inp in fn["inputs"])
    print(f"{fn['name']}({types})  selector={fn['selector']}  source={fn['source']}")
```

## How Fusion Picks A Signature

For a selector such as `a9059cbb`, a public signature database can return both
real and spam candidates:

```text
workMyDirefulOwner(uint256,uint256)
transfer(address,uint256)
```

If evmole sees an `address,uint256` argument structure, fusion picks
`transfer(address,uint256)`. If evmole can only recover a coarser shape, the
signature database still supplies the exact ABI type.

This is the core reason the tool improves over raw evmole on exact parameter
types.

## Project Layout

```text
abifusion/
  core/                  # Pure, I/O-free fusion engine (fuse_abi)
  fusion.py              # ABIFusion orchestrator, recommended path
  adapters.py            # evmole bytecode-analysis adapter
  ports.py               # adapter interfaces (Protocols)
  cli.py                 # abifusion entry point
  utils/                 # Signature lookup and bytecode helpers

tooling/abifusion_legacy/ # Research-only offline reconstructor, DB, data, features
schema/                  # Language-neutral JSON Schemas (output + tables)
rust/                    # Rust port (abifusion-core + abifusion crates)
scripts/eval/            # Evaluation and diagnostics
eval_output/             # Generated evaluation reports
tests/                   # Unit, integration, and conformance tests
```

## Current Limitations

- **No output recovery.** Function return values are not recovered.
- **Coverage-bound.** Unknown selectors absent from openchain/4byte and missed by
  evmole cannot be recovered reliably from bytecode alone.
- **Dynamic dispatch is hard.** Proxy patterns, delegatecall routers, and custom
  dispatch tables may need separate handling.
- **Network helps.** Fusion works best with signature DB access; the offline path
  is useful but less accurate.
- **Verified ABI lookup is separate.** Address mode fetches bytecode through RPC;
  it does not yet use Sourcify/Etherscan as a Tier 0 verified ABI lookup.
