# 01 — Literature Map

**Corpus:** 240 unique papers across 5 sources (OpenAlex, arXiv, Crossref, Europe PMC, Semantic Scholar), 109 blockchain/EVM-relevant. No retracted papers flagged.

## Terrain

The field of EVM bytecode-to-ABI reconstruction sits at the intersection of decompilation, type inference, and smart contract security. The literature reveals three distinct methodological families:

**Static analysis** dominates the early work. Chen et al.'s **SigRec** (2021, IEEE TSE, 38 citations) established the baseline: recovering function signatures from bytecode by analyzing how selectors are compared in dispatch patterns, then using the 4byte.directory database to resolve selectors to candidate signatures, and applying type inference via data-flow analysis of PUSH4 and EQ instructions to disambiguate parameter types. **EthIR** (2018) provides a framework for high-level bytecode analysis by decompiling EVM bytecode to a rule-based representation. **Elipmoc** (2022, PACMPL/OOPSLA, 33 citations) advances decompilation quality through hybrid techniques combining static analysis with symbolic execution to recover types, control flow, and storage layouts. More foundational still, **"Precise static modeling of Ethereum memory"** (2020, PACMPL, 21 citations) and work on **sound CFG construction** for EVM bytecode (EVMLiSA 2025, "Analyzing Smart Contracts: From EVM to a sound Control-Flow Graph" 2020) address the prerequisite problem: you cannot recover an ABI if you cannot reliably determine which code blocks belong to which function.

**Machine learning and deep learning** approaches emerged as a response to the brittleness of pure static analysis. **Neural-FEBI** (2023, JSS, 12 citations) uses neural networks for function boundary identification in bytecode — a critical precursor to ABI recovery. **Nimbus** (2022) proposes multi-task learning to speed up signature recovery via input resizing. Most recently, LLM-based approaches appear: **"Decompiling Smart Contracts with a Large Language Model"** (2025, arXiv) and **SCDBench** (2026, arXiv) proposing benchmarks specifically for LLM-based decompilers. A parallel thread uses deep learning on bytecode for vulnerability detection (**"Smart Contract Vulnerability Detection Using Deep Learning Algorithms on EVM bytecode"**, 2024), sharing feature extraction techniques with ABI recovery.

**The adversarial query** surfaced important cautionary work. **"When Function Signature Recovery Meets Compiler Optimization"** (2021, IEEE S&P, 20 citations) demonstrates that compiler optimizations (specifically Solidity's `--optimize` flag) systematically break static signature recovery by eliminating the dispatch-pattern artifacts SigRec and similar tools depend on. **"Abusing the Ethereum Smart Contract Verification Services for Fun and Profit"** (2023, arXiv) highlights how the 4byte.directory — the backbone database for selector resolution — can be poisoned with misleading entries. **"Seeing Through EVM Bytecode Obfuscation"** (2026, IEEE Access) addresses adversarial bytecode that deliberately resists decompilation.

**Open disagreements and gaps:**
1. **Static vs. ML tradeoff:** SigRec claims high precision but admits brittleness under optimization; Neural-FEBI and LLM approaches claim robustness but at the cost of requiring training data that may not represent adversarial or obfuscated contracts.
2. **Selector ambiguity is fundamental:** No approach escapes the fact that keccak256 hashes are preimage-resistant — the 4-byte selector provides 2^32 possible values, but the space of valid Solidity signatures is effectively infinite. All methods depend on external databases (4byte.directory, Etherscan verified contracts) for resolution, creating a single point of fragility.
3. **No unified benchmark exists** (though SCDBench 2026 is a first attempt). Comparisons between SigRec, Elipmoc, Neural-FEBI, and tool-level approaches (evmole, heimdall) are absent from the academic literature.
4. **Parameter type recovery** (beyond the selector) receives far less attention than function identification. Most work focuses on *which* functions exist, not *what types* their parameters are.
5. **Dynamic/tracing approaches** (using transaction traces to infer likely function usage) are underrepresented — the literature skews heavily toward static analysis of deployed bytecode.
